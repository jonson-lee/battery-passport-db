## 2 六类对象与身份

| 对象 | 本轮职责与分类 | v0.1 暂用身份 | 身份说明与待确认项 |
|---|---|---|---|
| 电池组（`BatteryPack`） | 可登记、维护和引用的电池组，实物实体。 | 组编码（`pack_code`） | 暂作为唯一业务组编码；全项目唯一性、换成员后是否沿用身份由①④确认。 |
| 成员安装（`BatteryPackUnit`） | 某单元在某组的一次安装发生，关联实体。 | 关联的 `pack_code`、关联的 `unit_code`、`occurrence_no` 共同标识。 | `occurrence_no` 是同一组与单元组合内的安装序次；它与两个父对象身份共同区分重复加入。仅两个父编码不足以区分历史。此标识是候选方案。 |
| 实际组装作业（`AssemblyJob`） | 一次已实际开始的初装或重组，过程实体。 | 作业编码（`job_code`） | 不包括尚未执行的计划或工单。 |
| 实际维护事件（`MaintenanceEvent`） | 已发生维护的问题、措施与结果，拟为事件子类型。 | 继承 `LifecycleEvent.event_id` | 不另造一套维护身份；每条维护就是同一条生命周期事件的维护专属部分。 |
| 组级检查（`PackInspection`） | 对实际组及其某次组成的检查，检查事件实体。 | 检查编码（`inspection_code`） | 与②统一检查框架后可能成为共享检查类型下的组级表达；不重复计数。 |
| 业务使用决定（`ServiceRelease`） | 对指定组成和用途作出的允许、拒绝或暂缓使用决定，决定事件实体。 | 决定编码（`release_code`） | 独立留档是否必要待评审；决定不同于检查结果和租赁合同状态。 |

电池单元（`BatteryUnit`）、组织（`Organization`）、生命周期事件（`LifecycleEvent`）由①主责。第四板块引用这些对象，不复制单元主数据、组织主数据或另设同义身份。用途暂由明确属性引用表达；本稿不自行新增用途要求（`ApplicationRequirement`）实体。

## 3 属性字典

以下字段名用于统一概念含义，并非已经确定的数据类型、外键或表列。标注“必需”表示 v0.1 对完整业务记录的建议要求；未知事实不能以编造值补齐，应保留缺失原因，是否允许不完整草稿需另行统一。①提供的单元身份不受本板块合成数据标签覆盖。

### 3.1 通用记录信息

| 属性 | 含义与建议可选性 |
|---|---|
| 数据来源（`data_origin`） | 本轮六类对象的模拟记录均须为 `synthetic`。引用的真实公开单元与其检测记录保留自己的来源。维护可从父事件继承来源标记，不能在两层维护冲突值。 |
| 录入时间（`recorded_at`） | 信息实际录入或补录的时间，完整记录必需。与实际发生时间分别保存。维护从父事件继承；如父事件缺少该属性，向①提出扩展。 |
| 来源引用（`source_ref`） | 报告、课堂样例或原始业务凭据的可追溯引用；有外部证据时必需，无凭据的合成样例注明样例来源。引用不表示将多个对象 ID 填入一段文本。 |
| 更正理由（`correction_reason`） | 更正已经被检查或决定采用的历史时必需；保留更正记录及影响说明的方式待共享事件模型统一。 |

### 3.2 电池组（BatteryPack）

| 属性 | 含义与建议可选性 |
|---|---|
| 组编码（`pack_code`） | 业务组编码，必需；候选身份。 |
| 型号（`model_name`） | 型号名称；未知可缺失并说明。 |
| 形成时间（`formed_at`） | 实际形成时间；已登记但尚未形成的组可缺失。不能替代多次组装作业的历史。 |
| 设计要求（`design_requirements`） | 设计要求属性组，记录具体要求值、单位及依据引用或版本；实际采用的要求必须可追溯。它不是独立规格实体。 |
| 铭牌额定参数（`nameplate_ratings`） | 铭牌额定参数属性组；与设计目标和检查实测值分开，未知可缺失。 |
| 业务状态（`business_status`） | 当前实物/业务使用限制状态，完整记录必需；标签由①④统一。不能直接写入合同占用或以此唯一推导可出租性。 |
| 状态理由（`status_reason`） | 当前限制或停用理由；有相应状态时必需，并衔接①的状态变更事件。 |

所有者通过 `Organization` 联系表达，不在组上复制组织名称或再存成员 ID 列表。设计要求一旦被历史检查采用，不得静默覆盖旧依据。

### 3.3 成员安装（BatteryPackUnit）

| 属性 | 含义与建议可选性 |
|---|---|
| 安装发生序次（`occurrence_no`） | 同组同单元的一次安装序次，必需；与所关联父对象身份共同标识。 |
| 安装位置（`position_code`） | 本次安装位置，必需；位置编码方式由④确认。 |
| 加入时刻（`joined_at`） | 安装开始生效的实际时刻，必需。 |
| 移出时刻（`removed_at`） | 本次安装结束生效的实际时刻；仍在组内时为空。 |
| 加入原因（`join_reason`） | 加入原因，完整记录必需。 |
| 移出原因（`remove_reason`） | 移出原因；发生移出时必需。 |
| 加入／移出业务顺序（`join_order` / `remove_order`） | 同一时刻存在无法仅靠时间区分的变化时，分别记录业务顺序；无需时可缺失。 |
| 来源缺失理由（`source_missing_reason`） | 已知存在安装/移出但历史主要执行来源无法取得时必需。允许缺失是历史资料例外，不是合成案例跳过追溯的理由。 |

所属组、单元和主要执行来源均由联系表达。成员评估仍引用③的评估事实；不在本对象增加一套独立的 `eligible` 判断。

### 3.4 实际组装作业（AssemblyJob）

| 属性 | 含义与建议可选性 |
|---|---|
| 作业编码（`job_code`） | 实际作业业务编码，必需；候选身份。 |
| 作业类型（`job_type`） | `initial_assembly` 或 `reassembly` 等作业类别，必需；标签待确认。 |
| 实际开始时间（`started_at`） | 实际开始时间，必需。尚未开始的计划不登记为本轮作业。 |
| 实际结束时间（`ended_at`） | 实际完成时间；作业仍在执行时可缺失。 |
| 过程摘要（`process_summary`） | 实际执行过程摘要，完整记录必需。 |
| 执行结果（`execution_result`） | 已完成作业的结果；执行中可缺失，不把“完成”解释为检查通过或允许使用。 |

执行组织用与共享 `Organization` 的联系表达。作业可能从属于一次维护；所属组与维护所属组必须一致。

### 3.5 实际维护事件（MaintenanceEvent）

| 属性 | 含义与建议可选性 |
|---|---|
| 继承的 `event_id` | 与父事件同一身份，必需，不增加独立 `maintenance_id`。 |
| 继承的 `started_at` / `ended_at` | 实际维护开始与结束；开始必需，未完成时结束可缺失。建议①让父事件支持这对时间，合图前确认。 |
| 继承的目标组与执行组织联系 | 维护的组级目标、通用责任/执行方从父事件继承。父事件必须支持组级目标；不在子类型重复维护同义联系。 |
| 维护类别（`maintenance_type`） | 实际维护类别，必需；具体类别待业务确认。 |
| 问题摘要（`problem_summary`） | 发现的问题或开展维护的原因，必需。 |
| 处理措施（`action_summary`） | 实际处理措施，必需。 |
| 执行结果（`execution_result`） | 执行结果；完成时必需，未完成可缺失。 |

本稿只展示 `MaintenanceEvent` 这一子类，使用部分特化：允许生命周期事件属于别的业务类型。全局子类集合及 `d/o` 互斥/重叠由①统一，不能仅凭局部单分支推定。父事件的身份、实际时间、录入时间、通用来源和组织关系均由子类继承。

| 属性 | 含义与建议可选性 |

| 实际检查时间（`inspected_at`） | 实际检查发生时间，必需；补录不改变它。 |
| 组成基准时点（`composition_as_of`） | 被检查实际组成的基准时点，必需；不得直接使用当前成员。 |
| 组成顺序（`composition_order`） | 基准时点存在多次变化且时间本身无法区分时必需。 |
| 检查方法及版本（`method_ref` / `method_version`） | 检查方法及所用版本，完整记录必需；与②统一口径。 |
| 观测摘要（`observation_summary`） | 实际观测摘要，完整记录必需；真实参数未知时明确未知，不编造阈值。 |
| 检查结果（`inspection_result`） | 本次检查结果，检查完成时必需；标签由②④统一，不兼作业务允许使用决定。 |

## 4 联系与双向数量

下表中的数量均为 v0.1 建议。表内“每个 A 对应多少 B”给出可选性，不能只看 `1:N` 推导业务条件。

| 联系 | 双向数量与读法 | 附加条件 |
|---|---|---|
| 组—成员安装 | 一个组有 `0..N` 次历史安装；每次安装对应恰好 `1` 个组。 | 草稿组可尚无成员。 |
| 单元—成员安装 | 一个单元有 `0..N` 次历史安装；每次安装对应恰好 `1` 个单元。 | 允许离组后再次加入，时间不重叠另作约束。 |
| 组—实际组装 | 一个组有 `0..N` 次作业；每次作业针对恰好 `1` 个组。 | 已实际开始才存在本轮作业。 |
| 组—实际维护 | 一个组有 `0..N` 次维护；每次维护针对恰好 `1` 个组。 | 通过维护继承的父事件目标联系承载；父事件可有其他类型目标，由①处理全局规则。 |
| 组—组级检查 | 一个组有 `0..N` 次检查；每次检查针对恰好 `1` 个组。 | 对象是实际组成，非仅指一个不变的组编码。 |
| 组—业务使用决定 | 一个组有 `0..N` 次决定；每次决定针对恰好 `1` 个组。 | 可按不同用途或组成多次决定。 |
| `AddedByJob` | 每次安装由 `0..1` 次作业直接引起加入；一项作业可引起 `0..N` 次安装加入。 | 与 `AddedByMaintenance` 配成加入来源 XOR。 |
| `AddedByMaintenance` | 每次安装由 `0..1` 次维护直接引起加入；一次维护可引起 `0..N` 次安装加入。 | 经维护中的作业引发时，不再直接登记维护来源。 |
| `RemovedByJob` | 每次安装由 `0..1` 次作业直接引起移出；一项作业可引起 `0..N` 次安装移出。 | 与 `RemovedByMaintenance` 配成移出来源 XOR。 |
| `RemovedByMaintenance` | 每次安装由 `0..1` 次维护直接引起移出；一次维护可引起 `0..N` 次安装移出。 | 未移出的安装没有移出来源。 |
| 作业—所属维护 | 一项作业属于 `0..1` 次维护；一次维护包含 `0..N` 项作业。 | 独立初装无所属维护；同一成员变化只记一个主要来源。 |
| 作业—触发检查 | 一次作业触发 `0..N` 次检查；一次检查有 `0..1` 次主要触发作业。 | 与维护触发合计最多一个来源。 |
| 维护—触发检查 | 一次维护触发 `0..N` 次检查；一次检查有 `0..1` 次主要触发维护。 | 定期检查可两者均无；维护中的重组按一个主要来源留档。 |
| 决定—依据检查 | 一次决定引用 `0..N` 次检查；一次检查被 `0..N` 次决定引用。 | M:N；允许使用需具备要求的同组同组成检查，零证据例外见下文。 |
| 组织—拥有组（合图接口，未在本稿展开） | 所有者引用①的 `Organization`；当前所有权数量及是否支持共同所有待①④确认。 | 本稿不自行规定恰有一个所有者；共享资产登记和历史转移由①协调，合图时补足联系。 |
| 组织—执行作业 | 一个组织执行 `0..N` 项作业；每项作业暂建议恰有 `1` 个主要执行组织。 | 多参与方通过共享角色机制协调，不能与主要责任方含混。 |
| 组织—执行检查 | 一个组织执行 `0..N` 次检查；每次检查暂建议恰有 `1` 个主要执行组织。 | 与②统一。 |
| 组织—作出决定 | 一个组织负责 `0..N` 次决定；每次决定暂建议恰有 `1` 个责任组织。 | 是否还需具体责任人员由①协调。 |
| 组织—维护执行方 | 一个组织执行 `0..N` 次维护；每次维护暂建议恰有 `1` 个主要执行组织。 | 在父事件层表达并继承，不另建重复维护组织联系。 |

### 4.1 来源 XOR 的精确含义

对每次成员安装，**加入**和**移出**分别检查来源。两组不能合并成“这条成员记录只能有一个执行来源”，因为加入可能由 J1 引起，而后来移出由 M1 引起。

- 已知加入来源时，`AddedByJob` 与 `AddedByMaintenance` 恰有一个；未知历史可两者均无，但必须记录缺失原因。
- 已发生移出且来源已知时，`RemovedByJob` 与 `RemovedByMaintenance` 恰有一个。尚未移出时两者均无；未知移出来源仍需缺失原因。
- 如果重组 J2 属于维护 M1，变化直接归 J2，维护通过 J2 追溯。不得对同一变化再直接登记 M1。
- 四条来源联系的对象组必须与成员安装所属组一致。一次不更换成员的维护可以四类变化均为零。

一项检查的“主要触发作业”与“主要触发维护”合计不超过一个。各自写 `0..1` 并不足以表达这一跨联系限制，所以图旁规则和本节需随图一起评审。

检查及其主要触发作业或维护必须针对同一组；属于维护的重组作业也必须与该维护针对同一组。③的资格输入目前仅定义为读取边界，采用哪条评估、如何将评估证据联系到安装或组装作业，仍待③④合图确认。本稿没有宣称已完成这条结构化证据链。

### 4.2 检查证据与使用决定

`ServiceRelease` 与 `PackInspection` 的 M:N 联系用于保存结构化证据关系，不用逗号分隔的报告编号代替。总体最小基数允许为零，是为了容纳因缺少证据而拒绝或暂缓的决定；这不意味着允许使用可以没有必要证据。

允许使用须引用规定的同组、同实际组成检查，并满足对应用途依据；所需检查集合由②③④⑤确认。拒绝或暂缓可以不引用检查，但须保存缺失理由。引用多份报告时，每份证据的组成与适用条件都需要核对，不能仅因组编码相同就采用。

## 5 时间与历史规则

| 规则 | v0.1 的表达与检查方式 |
|---|---|
| 安装有效区间 | 暂用半开区间 `[joined_at, removed_at)`；`removed_at` 为空表示仍有效。若存在同刻变化，以 `(时刻, 业务顺序)` 作为有序端点，并按同一顺序定位组成；移出端点必须晚于加入端点，不能用两个相同端点掩盖不同状态。 |
| 防止重叠 | 同一单元不得有重叠有效安装；同一组同一位置不得同时有两个有效成员。这些是跨记录时间规则，普通基数无法保证。 |
| 历史还原 | 用组、`composition_as_of` 及必要的 `composition_order` 选出当时有效安装，得到实际组成。不能用当前成员回填历史检查和决定。 |
| 发生与录入 | `inspected_at`、`decided_at`、实际作业/维护时间描述业务事实；`recorded_at` 描述录入。补录只改变录入事实，不把检查时间移到当天。 |
| 组成证据一致 | 检查基准时点所还原的组成必须是实际受检组成；决定须明确其采用的组成。检查后如果成员改变，旧决定不自动适用于新组成。 |
| 依据可追溯 | 保留当次检查采用的要求值或不可被静默替换的依据版本；只保存当前设计参数不足以重建历史判断。 |
| 历史更正 | 不直接覆盖已被采用的安装或依据。记录更正原因，并检查受影响的检查和决定；具体更正机制待合图确认。 |
| 升级条件 | 如果安装历史加时点/顺序仍无法唯一定位实际组成，重新评审 `PackConfiguration`，不能以“按当前成员”作为退路。 |

上述规则对应需求 REQ-T01–REQ-T06，仍为待评审建议。换成员后组身份是否延续、哪些维护必须复查、旧证据何时可复用、租期内能否维护或改组，不能从本图自行推定。

## 6 简短合成时间线核验

以下编号只是课堂样例，均标为 `data_origin = synthetic`。时间顺序仅用于说明模型可表达性，不提供电气阈值或安全结论，也不假定租期内可以改组。

| 顺序 | 业务事实 | 模型应能保留的结果 |
|---|---|---|
| T1 | J1 为 P1 初装 U1、U2；两次安装序次均为 1。 | 两条安装各直接 `AddedByJob=J1`，无移出；保存不同位置。 |
| T2 | I1 检查 T1 后的组成，R1 针对用途 A 和依据 V1 引用 I1。 | R1 还原 U1、U2；检查结果与决定结果分别保存。 |
| T3 | 经④⑤确认租赁处理后，M1 执行换件；其重组 J2 移出 U1、加入 U3。 | U1 旧安装 `RemovedByJob=J2`；U3 新安装 `AddedByJob=J2`；J2 属于 M1，不再把同一变化直接登记为维护来源。 |
| T4 | I2 检查变化后的组成，R2 引用 I2。 | R2 还原 U2、U3；查询旧 R1 仍还原 U1、U2。 |
| T5 | M2 仅作不换成员维护。 | M2 可以存在而没有任何安装变化；是否复查由已确认规则决定。 |
| T6 | U1 日后再次加入 P1。 | 建立 `(P1,U1,2)`，不覆盖 `(P1,U1,1)`；再次加入前须满足不重叠及位置规则。 |

另需检查：一条因证据缺失而拒绝或暂缓的决定可以没有检查引用，但保存理由；一条定期检查可以没有主要触发执行记录。这两种例外不会把允许使用的证据条件取消。

本轮完成的是上述表达与一致性核验的设计说明；尚未生成完整 CSV 样例或执行数据库查询验证。

## 8 组内讲解主线
