## 业务边界

用户已确认以中国大陆现行政策限定业务场景。现有公开实验数据仍按 `BatteryUnit` 的电芯粒度解释；本轮不把电芯改称模组，不声称已经掌握真实企业组包、维修或租赁数据。新增运营记录继续使用 `data_origin = synthetic`。

本板块覆盖组包产品身份、设计要求、组成历史、初装与重组、维护安排与执行、检查证据和业务使用放行。来源接收、原始资产登记、单元诊断、单元用途资格、储能项目和合同由相应板块维护。本板块可以提出共享实体的补充需求。

“完整”以这条业务链能够解释清楚为标准。先辨识必要对象，再决定能否在明确范围内合并；早期约十至十二个实体的数量目标不用于排除已经识别出的必要事实。

## 中国大陆现行政策对业务边界的影响

六部门令第73号《新能源汽车废旧动力电池回收和综合利用管理暂行办法》自2026年4月1日施行，同时废止2021年《新能源汽车动力蓄电池梯次利用管理办法》。旧办法中的梯次利用要求不能直接作为当前义务引用。现行办法涉及动力电池单体、模块和包的编码，以及产品构成、维修更换、来源与去向等信息，这支持分别保留资产身份和变化记录。[现行办法，第9至12条、第24条及第50条](https://wap.miit.gov.cn/zcfg/jdcjxl/art/2026/art_640a0abfac6549feb6ead9c591b7680d.html)

2026年7月30日工信部第20号公告废止2024年行业规范条件中梯次利用有关条款，停止相关企业公告管理。利用废旧动力电池生产的电池产品仍须符合应用领域质量标准；电动自行车等领域受到禁止性限制。模型因此需要记录目标应用及其依据，不能仅根据“二手”或单元资格作出整组可使用的结论。[第20号公告](https://www.miit.gov.cn/jgsj/jns/wjfb/art/2026/art_945f3df30a984763877679740ff296a3.html)

工信部解读还提及100kWh以上储能系统等相关禁用领域。GB 44240-2024官方目录显示该强制性标准自2025年8月1日实施，当前标为现行。具体适用对象、能量边界和条款应结合标准全文与明确产品核对；不能据此反推较小容量就自动允许，也不能用单个包容量代替其所在系统及应用条件。[工信部解读官方转载](https://jxj.beijing.gov.cn/ztzl/ywzt/jnhbfwpt/jnhbgzdt/202607/t20260731_4803637.html)、[国家标准官方目录](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=8E520B1991C62DEBC55B46DE49C6F4F5)

当前尚未选定具体备电或储能产品、场所及适用标准。本轮可以完成业务对象分析，生产用途和出租条件仍须由第三、第五板块共同核实。本项目的 `ServiceRelease` 表示有责任人的业务使用决定，不代表法定认证、型式试验合格或行政批准。

## 从行业流程识别业务对象

二手动力电池再次使用存在整包复用、拆至模组后重组、拆至电芯后重组等路线，并非每个包都依次经历全部拆分层级。原始研究比较了这些路线及其对BMS、热管理、重组和维修的不同要求。因此，模组和电芯不能只因都叫 unit 就被当作同一种实物。[IREC等机构原始研究，第4节](https://www.nlr.gov/docs/fy22osti/84527.pdf)

一个需要重组的案例通常要依次回答下列问题。该顺序用于分析信息需求，不是实际电气操作规程。

1. **识别来源及处理路线。** 哪个来源包或单元进入系统，能够核实哪些历史，采用整包、模组还是电芯路线；无法满足要求的对象转交相应回收处置流程。
2. **明确应用要求。** 拟用于何种设备和场所，需要什么电压、能量、功率、环境条件及适用依据；来源数据能否支撑判断。
3. **筛选并形成设计。** 根据已有检测、资格及兼容性证据选择成员，形成目标规格；SOH单一数值不能代替全部判断。
4. **执行组装并记录实际组成。** 保存执行组织、过程及结果，知道实际安装了什么、安装在哪里；计划成员与实际装入成员可能不同。
5. **检验成组产品。** 保存对实际产品及其配置进行的检查和报告，再记录是否允许进入某项业务用途以及限制。

上述检验环节有独立业务意义。UL对再利用设施的说明区分筛选分级流程与再利用产品面向最终用途的测试认证；这可用于理解“单元经过筛选”和“最终产品满足用途要求”的区别。UL材料不作为中国大陆市场准入依据。[UL官方说明](https://www.ul.com/news/ul-certification-helps-promote-repurposing-electric-vehicle-ev-batteries)

投入使用后，维护可由计划、检查发现、报警或使用方报修触发。需依次保存受理安排、实际操作、检查证据及恢复使用的决定。Sandia的数据指南区分纠正性维护、定期检查和预测性维护，并关注诊断、维修和停机记录；这些是通用运维信息需求。[Sandia数据指南，第5.1.2节](https://www.sandia.gov/app/uploads/sites/273/2023/04/Energy-Storage-Data-Submission-Guidelines-SAND-Report.pdf)

维护不一定更换电池成员。SMA的特定储能产品手册分别列出连接检查、外观检查、柜体/BMS/模组维护、状态记录和重新投运步骤，说明一次维护可以包含多项动作；该手册只用于验证业务对象的区别，不作为本项目产品的操作要求。[SMA维护程序](https://manuals.sma.de/ESSX-20/en-US/12407377547.html)

## 修订后的业务对象分类

以下是应用课程规则后的项目建议。先判断要记录的业务事实及其归属，再选择图形与标识；不预设每项都必须对应一张表。

| 前轮名称 | 当前分类及建议 | 属性或联系应如何理解 | 何时需要独立实体 |
|---|---|---|---|
| `BatteryPack` | 保留实物实体 | PackCode、型号、形成日期、铭牌参数等是属性；P1是一个实例 | 项目明确要独立登记、租赁和追踪电池组，理由充分 |
| `BatteryPackUnit` | 优先作为成员安装联系的关联实体候选 | 单元与组的某次安装拥有位置、加入/移出时间及原因 | 关联实例需保留组成历史；不是第三类独立电池实物 |
| `MaintenanceEvent` | 保留实际维护的事件实体候选 | 类型、发现的问题、处理措施、结果是事件属性 | 项目明确需要保存每次维护记录；是否用事件子类型随后评审 |
| `PackSpecification` | 普通或复合属性优先，撤回无条件核心地位 | 目标电压、容量、能量、串并联要求、环境要求等先判断各自属性归属 | 若组织将规格本身作为需记录的概念对象，可保留实体；跨产品复用和修订是支持理由，并非必要条件 |
| `PackConfiguration` | 撤回无条件核心地位，先比较组成历史表达 | 某时点的成员清单可能由安装联系历史重建；VersionNo本身是属性 | 若业务把具体组成版本作为需记录的对象，可建版本实体；签署不是必要条件，强弱取决于业务标识规则 |
| `AssemblyJob` | 条件过程实体 | 仅保存初装日期时可为包的属性；组装者是对组织/人员的联系 | 保存实际作业过程及其专属信息即可支持实体候选；计划、取消和返工管理是进一步支持理由 |
| `PackInspection` | 条件检查事件实体，需与第二板块协调 | 当前检查日期/结论可以是摘要属性，但不能代替多次检查历史 | 需要独立保存每次组级检查、观测与报告时成立；优先复用已有检测框架 |
| `ServiceRelease` | 结论属性或审批联系优先，撤回无条件核心地位 | 单次检查附带的批准结论、日期、理由可为属性；批准方是联系 | 若决定本身需要留档，可建决定事件；重复、撤销和单独引用是支持理由，并非必须全部存在 |
| `MaintenanceWorkOrder` | 条件任务实体 | 计划日期、优先级、工单状态是该任务的属性 | 维护任务本身需与执行事实分别留档时可成立；受理、派工和取消是示例，只登记实际维护时无需预设工单 |

前轮加入的“规格复用”“配置签署”“工单取消”“独立审批撤销”等是扩展假设，尚未经过全组需求确认。不能用自己提出的扩展功能反过来证明这些实体已经必需。这些也不是实体成立的硬门槛：仅服务一个包的规格、未经签署但需留档的配置、只记录实际完成过程的作业，都可能成为合理实体。应判断组织实际要记录的对象、实例和专属信息，并比较属性或联系表达是否足以保留语义。

## 属性应挂在哪里

| 信息 | 建议归属 | 课程分类及限制 |
|---|---|---|
| 组编码、型号、形成日期 | `BatteryPack` | 普通属性，标识符须由业务唯一性确定 |
| 铭牌额定电压、额定容量、额定能量 | `BatteryPack` 或被明确引用的产品规格 | 普通属性；铭牌值、设计值与实测值须区分 |
| 目标电压、容量、能量及环境要求 | 明确的设计要求对象或包的规格属性组 | 可用复合属性组织；并非天然独立实体 |
| 成员安装位置、加入时间、移出时间及原因 | 成员安装联系或关联实体 | 联系属性；同一个电芯换组或再次装入时取值可不同 |
| 维护类别、问题描述、处理措施、结果 | `MaintenanceEvent` | 普通属性；只有需逐项查询重复操作时，再考虑复合多值属性或动作明细 |
| 检查方法、检查日期、报告引用、检查结果 | 实际检查记录 | 该次检查的属性；检查人/机构已有实体时用联系表达 |
| 批准结论、批准时间、理由 | 检查/评估记录，或明确的审批联系 | 若审批被独立管理则另行评审决定事件，不能两处重复维护同一结论 |
| 当前成员数量 | 成员历史在某时点的统计 | 派生属性，统计时点及有效区间规则须明确 |
| 当前可出租性 | 有效用途结论、检查、停用条件和合同占用的综合判断 | 条件确认后可作派生属性；不能仅从某次维护完成推出 |

单个包有多个目标参数，不等于多个规格实体；多个参数可共同描述一个对象。多个安装位置也不能简单作为包的多值属性来替代成员联系，因为需要知道每个位置安装的是哪个已有单元。

## 当前可以保留的建模基础

明确保留 `BatteryPack` 作为实物实体，并引用第一板块的 `BatteryUnit` 和 `Organization`。实际维护记录保留为 `MaintenanceEvent` 事件候选。成员安装以 `BatteryPackUnit` 作为关联实体候选，或先以带属性联系分析；正式画法随后统一。这样既不是把九个名词都画成矩形，也不是把全部运维历史压成包上的几个当前值。

同一单元可能多次加入同一组。仅用“包标识＋单元标识”不能区分这些安装发生；需要安装发生次序、足以区分的时间或其他业务标识。最终是否使用独立代理键属于后续标识/逻辑设计选择，不能改变“它表达的是一次联系”的含义。

实际维护先定义为一次需要独立留档的已发生维护作业，记录范围由业务确认，不强制拆成每项动作一条实体。若一次作业内要逐项保存操作时间、执行者、旧件和新件，应评审动作明细或关联结构。工单代表待办任务，实际维护代表执行事实，两者只有在任务管理进入范围后才同时保留。

组级检查信息仍是业务缺口：现有公开 `DiagnosticTest` 面向电芯，不能直接充当组级验收。若项目保留初装/修后检查流程，就必须记录各次组级检查及证据；由现有检测框架扩展还是新增检查事件，需要第二板块共同确认。这里只调整它的建模归属，不取消这个业务需要。

## EER画法的课程约束

概念图采用本课Chen式实体、属性、联系记法，并统一课件的最小/最大基数符号。普通实体用矩形，属性用椭圆，标识属性下划线；复合属性连接组成属性，多值属性双椭圆，派生属性虚线椭圆；联系用菱形，关联实体用矩形包菱形，弱实体用双矩形。不要将关系表列、SQL数据类型和外键清单当作概念模型的替代。

`MaintenanceEvent ISA LifecycleEvent` 可以继续评审，因为实际维护可以是生命周期事件的一种，并有维护专属信息。必须确认两者是同一个事件实例，维护继承通用事件的标识、属性及联系；事件编号、发生时间、通用对象和组织信息不在子类型重复定义。若父事件只能指向电芯，而维护要指向组，须先调整父层适用对象，不能靠一条ISA线掩盖矛盾。

`BatteryPack` 包含 `BatteryUnit`，`PackConfiguration` 描述一个组，检查针对一个组，工单安排实际维护，均不能因存在依赖而直接画ISA。状态枚举也不自动产生子类型；是否特化应证明存在有业务意义的子群及专属属性或联系。

如果以后保留配置实体且其局部版号只有在包内才唯一，可以评审为由包标识加版号识别的弱实体；有独立业务版本编号则需按另一识别规则审查。子类型继承主键和弱实体借助owner识别是不同概念。

继承结构确定后，再分别判断disjoint/overlap及total/partial，不能把两者混成一个选择。LN4第26至27、31、37至40页分别说明判别条件、互斥性和完全性；本轮不以增加子类型数量作为EER目标。

| 用途要求及其依据 | 第三和第五板块主导，是否使用 `ApplicationRequirement` 另审 | 场景、产品类别、规模、适用标准/业务要求及版本，供设计、评估和放行引用 |
| 储能系统或具体部署设备 | 第五板块评审是否使用 `StorageSystem` | 项目实际对应的物理系统及规模；项目包含多个系统时，不能用项目名代替设备边界 |
| 责任人员或签署记录 | 共享需求，第一板块协调 | 谁执行、检查或作出决定；需要查询个人跨作业责任时设独立人员实体 |

用途要求与组包规格不同：前者是应用提出的条件，后者是为满足这些条件设计的产品要求。可以先只支持一个经明确的应用要求版本；没有复用或历史查询需求时，不必建成完整法规标准库。

`StorageProject` 是业务项目，`StorageSystem` 是物理部署对象。如果明确一个项目只含一个系统，可以由项目保存明确的系统信息并约束范围；否则需要独立系统对象。本轮不预设两者必然相同，也不自动决定联系基数。

## 其他业务信息的条件分类

| 候选对象 | 何时需要成为实体 | 受限范围内怎样承载 |
|---|---|---|
| `BatteryModule` | 选择模组重组，或要按模组检测、替换、追溯时 | 电芯级课堂案例可暂不引入；不能把电芯重命名为模组 |
| `ModuleCellMembership` | 追踪模组内部电芯及其变化时，作为联系或关联结构评审 | 若模组作为不可拆追踪单元，不必保存内部全部成员 |
| `Component`、`ComponentInstallation` | BMS、接触器、风扇等有独立序列号及安装维修史时 | 简单案例保存部件类型、型号、数量和动作证据 |
| `MaintenanceIssue` | 一个缺陷跨多次检测/工单，或要分别跟踪多个问题时 | 单问题工单可保存问题摘要；报警不直接等于确认故障 |
| `MaintenancePlan` | 要生成周期任务、计算到期和逾期时 | 单次计划保存工单计划日期，不能宣称已支持周期计划 |
| `AssetHold` | 停用有独立原因、起止时间和解除责任，或需要分析停用区间时 | 与第五板块复用状态历史；不能只根据当前状态推算历史停机 |
| `InspectionItem` 或检测明细 | 需要查询多项目结果时，比较复合多值属性、弱实体或明细结构 | 优先复用第二板块；只保存报告引用时明确不支持测量明细查询 |
| `ComponentReplacement` 或换件明细 | 需表达多项换件时，先辨识参与对象、联系和专属属性 | 单一更换可由实际维护事件结构化保存旧件、新件和位置 |
| `DisassemblyJob` | 本系统实际管理来源包拆分及输出部件时 | 若只从已拆分可追踪单元开始，来源信息和拆分记录由第一板块衔接 |
| `AlarmOccurrence`、遥测记录 | 接入报警发生/确认/清除过程或持续监控时 | 保留工单触发引用及必要快照；不扩展完整BMS遥测平台 |
| 报告证据关联 | 同一决定引用多份报告时，优先作为联系分析 | 在联系设计阶段与第三板块证据模型协调，不在文本内保存报告ID列表 |

这些名称提示需要表达的信息，不是已经确认的实体清单。实体、联系、关联实体、弱实体和多值属性应逐项选择。最终范围要明确纳入哪些流程，不能用未纳入的对象暗示系统已支持相应功能。

## 状态应放在各自业务对象上

组的实物身份、配置是否已形成、检查结果、业务放行、维护任务状态和租赁状态分别描述不同事实。例如合同仍有效时，组可能因维护暂时停用；一次维护已经执行，也可能仍未通过修后验证。

可出租通常是多个事实的综合判断，还要考虑用途、当前配置、放行有效性、未解除的停用条件及合同占用。这是本项目待确认的业务规则，不是一个来源直接给出的通用标签。状态取值本身一般先作属性，不因每个值不同就创建一个实体或子类型。

## 用一个模拟案例检查分类

以下只用于检查信息归属，全部为课堂模拟，不给出实际配组参数或安全结论。

电池组P1、电芯U1和U2是实体实例；“U1在位置A于时间T1加入P1”是一项成员安装事实，位置A和T1属于这次联系。更换时保留U1的移出及U2的装入信息，不能直接覆盖电芯上的一个当前组编号而丢掉历史。

维护记录M1是一次已发生的维护实例；“维护类别=检查”“发现=连接异常”“措施=连接处理”“结果=待复核”是该实例的属性值，不能分别画成四个实体。若处理结果有多次独立复查，应保留每次复查事实，而非不断覆盖一个最新结果。

仅知道P1的额定电压、容量和组装日期，不足以推出需要 `PackSpecification` 或 `AssemblyJob`。如果业务进一步要求多个包共用设计S1、追踪作业J1从待执行到返工、管理被签署的配置V1及其检验，这些都是支持相应实体候选的业务理由；即使没有这些扩展，也应根据实际要留档的对象判断，不能机械排除。

## 进入联系和 EER 设计前的确认顺序

1. 与第三、第五板块明确中国大陆具体用途、产品和部署规模，核对适用依据；不能用“小型储能”四个字代替这一步。
2. 与第一板块保持电芯粒度，决定是否扩展模组或来源整包路线；扩展时分别保留真实实验和模拟层级的来源性质。
3. 按实体、属性、联系及关联结构逐项评审业务信息，确认记录粒度、标识条件及现有共享模型能否承载。
4. 确认是否独立管理配置版本、工单、可复用规格及审批决定；未纳入的扩展不能作为既成需求。明确检查与换件怎样定位到当时实际组成。
5. 然后列联系、最小/最大基数、可选性和时间约束，最后评审ISA、子类型完整性与互斥性及EER画法。
