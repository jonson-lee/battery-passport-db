# 第四板块「组包与维护管理」数据实现说明

更新日期：2026-11-20。状态：**数据快照已完成，可供全组合库、演示查询与报告使用**。  
实现方式：SQLite 数据快照（与第 1–3 板块交付方式一致）；课程最终实现平台仍为 PostgreSQL。  
上游输入：第三部分交接的 `data/Part3_Handover.zip`（含 `section3_eligibility_整合库.sqlite`）。  
模拟时间线：2026-11-19 19:00 至 2026-11-20 11:20 (+08:00)，数据快照时钟为 **2026-11-20 11:20**。  
所有第四板块业务记录均为 `data_origin = 'synthetic'`，不代表真实企业运行事实，也不是认证安全判定。

## 1 一句话结论

在第三部分 1,000 个电池单元、1,000 次资格评估之上，第四板块生成了 **160 个电池组、653 条成员安装、175 次组装作业、23 次维护事件、175 次组级检查、179 次使用决定、175 条决定-检查证据**，并把 23 条维护事件作为共享 `lifecycle_event` 的增量写回第①板块。所有成员安装均可通过 `assessment_id` 追溯到第③板块的**最终（final）第二利用评估**；第④板块没有修改第①–③板块的任何既有行。

## 2 上游数据核对：从 Part 3 到 Part 4 的可用单元池

第三部分交接说明指出，第四板块组包只需要第③板块的 `assessment_id`、`unit_id`、`final_purpose_id` 和 `status`。本实现据此建立可用单元池：

| 上游事实 | 数量 | 在第四板块的用法 |
|---|---:|---|
| `battery_unit` 电池单元 | 1,000 | 成员安装引用 `unit_id` |
| 资产注册状态 `registered` | 750 | 只有已登记单元可进入组包 |
| `ELIGIBILITY_ASSESSMENT` 评估 | 1,000（每单元 1 次） | 成员安装引用 `assessment_id` |
| 其中 `status = 'final'` | 750 | 只有最终评估可支持组包 |
| 其中 `final_purpose_id ∈ {1,…,9}` | **725** | 可作为二次利用组包池 |
| 其中 `final_purpose_id = 10`（拆解回收） | 25 | 不进入组包池 |
| `status = 'draft'`（对应 draft/retired 单元） | 250 | 不进入组包池 |
| `USE_PURPOSE` 用途 | 10（P01–P09 二次利用，P10 回收兜底） | `SERVICE_RELEASE.purpose_id` 引用 |
| `organization` 组织 | 20（制造商/回收商/运营商/出租方/实验室） | 作业、检查、决定的执行组织 |
| `lifecycle_event` 既有事件 | 1,200（1000 登记 + 150 所有权转移 + 50 更正） | 第四板块只**追加** 23 条 `maintenance` 事件 |

**组包判定规则（实现口径）**

> 一条成员安装可用，当且仅当它的 `assessment_id` 对应的评估同时满足：
> `status = 'final'`、`final_purpose_id BETWEEN 1 AND 9`、且 `ELIGIBILITY_ASSESSMENT.unit_id = BATTERY_PACK_UNIT.unit_id`。
> 数据来源标签为 `synthetic` 的安装必须填写 `assessment_id`（`BATTERY_PACK_UNIT` 的 CHECK + 触发器双重校验）。

字段总数 **82**（含 `data_origin`、`recorded_at`、`source_ref` 等来源字段）。字段级定义仍以《IBA6151 小组文件汇总》§4.2 数据字典为准；本文件只记录实现口径与差异。

### 4.2 主键类型与上游对齐（重要）

组内 2026-11-16 汇稿把 `pack_id`、`maintenance_id` 记为 `integer`。实际交接库中第①板块的 `lifecycle_event.event_id` 和 `lifecycle_event.battery_pack_id` 都是 **TEXT**（UUID v5），因此本实现做了必要对齐：

| 字段 | 汇稿写法 | 本次实现 | 原因 |
|---|---|---|---|
| `BATTERY_PACK.pack_id` | `integer` | **TEXT（UUID v5）** | 必须与 `lifecycle_event.battery_pack_id`（TEXT）同为可核对的外键目标；与第①板块 `battery_unit.unit_id` 的 UUID 代理键风格一致 |
| `BATTERY_PACK.pack_code` | `text` UQ | `SIM-PACK-0001`（TEXT UQ） | 可读业务编码，供文档、预览和第⑤板块引用 |
| `MAINTENANCE_EVENT.maintenance_id` | `integer`，继承父事件 ID | **TEXT（UUID v5）**，与 `lifecycle_event.event_id` 完全相同 | 维护是共享事件的子类型，父子必须共用同一个标识值；父表键为 TEXT |
| `BATTERY_PACK_UNIT.pack_unit_id` | `integer` | `INTEGER` 顺序代理键 | 仅板块内部使用 |
| `BATTERY_PACK_UNIT.unit_id` | 同第①板块 | TEXT，引用 `battery_unit.unit_id` | 与交接数据一致 |
| `BATTERY_PACK_UNIT.assessment_id` | 同第③板块 | INTEGER，引用 `ELIGIBILITY_ASSESSMENT.assessment_id` | 与交接数据一致 |
| `SERVICE_RELEASE.purpose_id` | 同第③板块 | INTEGER，引用 `USE_PURPOSE.purpose_id` | 用途字典与第③板块一致 |

> 合图/合库时若其他板块仍按 `integer pack_id` 设计，请以本快照为准改为 TEXT；第⑤板块直接引用 `pack_id`（UUID）即可，展示时用 `pack_code`。

### 4.3 完整性控制（SQLite 可执行层）

`sql/section4_schema.sql` 在表约束之外，用触发器补齐 SQLite 无法声明式表达的跨行规则：

1. **成员变化来源 XOR**：加入/移出各自恰好一个主要来源（作业或维护）；未知历史才允许 `source_missing_reason`。合成数据中该字段全部为空（即全部可追溯）。
2. **同组一致**：安装的加入/移出作业或维护、检查的触发作业或维护、作业所属维护，其目标电池组必须与安装/检查/作业所属组一致。
3. **资格证据**：`assessment_id` 必须对应同一 `unit_id` 的 `final` 且用途 P01–P09 的评估；`data_origin='synthetic'` 时不可为空。
4. **时间不重叠**：同一单元的有效安装区间、同一组同一位置的有效安装区间不得重叠（半开区间 `[joined_at, removed_at)`）。
5. **维护继承**：`MAINTENANCE_EVENT` 的父 `lifecycle_event` 必须是组目标、无单元目标、有执行组织的 `maintenance` 事件。
6. **证据一致**：`SERVICE_RELEASE_INSPECTION` 只允许连接同组、同 `composition_as_of` 的检查。
7. **组目标存在**：写入 `lifecycle_event.battery_pack_id` 时校验对应 `BATTERY_PACK` 已登记（对第①板块表只加触发器，不改数据）。

另有 8 个视图，核心接口视图：

- `V_PART4_ASSESSMENT_POOL`：第③板块评估池 + `is_assemblable` 标记（725 条为 1）。
- `V_PART4_PACK_CURRENT_COMPOSITION`：各组当前成员与所引用的评估。
- `V_PART4_PACK_SERVICE_STATE`：组当前业务状态 + 最近一次使用决定 + 当前成员数（**第⑤板块查询可出租性时建议使用**）。
- `V_PART4_RELEASE_EVIDENCE`：使用决定与其检查证据明细。
- `V_PART4_ALLOWED_RELEASE_WITHOUT_EVIDENCE` 等 4 个审计视图，正常应全为空。

## 5 组包与业务场景

### 5.1 组包策略

- **只使用第③板块最终评估且用途为 P01–P09 的 725 个单元**；250 个 draft 评估单元和 25 个 P10（拆解回收）单元明确不组包。
- 每个电池组的成员用途必须一致：组内所有成员的 `final_purpose_id` 都等于该组使用决定中的 `purpose_id`。
- 共组装 **160 个电池组**，使用 **638 个单元**；剩余 **87 个合格单元** 保留为未组装备件池（其中 14 个在后续维护换件中使用）。
- 组包规格以 4S1P 为主（4 个 3.3 V / 1.1 Ah 单元串联，约 13.2 V / 4.4 Ah / 58.1 Wh），P03 只有 2 个可用单元，因此保留 1 个 2S1P 小组；这些额定值是根据单元铭牌做的**算术组合**，不是真实组级测试结果。

### 5.3 维护与历史场景（覆盖验收要求）

1. **换件重组（14 组）**：维护 M 触发重组作业 J；旧成员在 J 结束时移出（`removed_by_job_code = J`），新成员在同一时刻加入（`added_by_job_code = J`），换入单元引用其自己的 `assessment_id`；随后对新组成做检查 I2 并以 I2 为证据作出新决定 R2。旧决定 R1 仍能还原旧组成。
2. **拆件未补（2 组）**：维护直接移出故障单元（`removed_by_maintenance_id`），组成由 4 个降为 3 个；维护后检查记录“已低于 4S1P 设计要求”，使用决定被拒绝，组状态转为 restricted / retired 各 1 个。
3. **返修重装（1 组）**：维护先移出故障单元；其后独立重组作业 J2 把同一单元重新装回，产生 `occurrence_no = 2` 的新安装（不覆盖历史），随后重新检查并放行。用于证明同组同单元的多次安装可以区分。
4. **不换件维护（5 组）**：维护执行了保养，但没有成员变化；其中 2 组在维护后重新检查并再次确认放行，证明“维护事实”与“成员变化”不是同义记录。
5. **进行中维护（1 组）**：快照时维护仍在诊断中（`execution_result IS NULL`），组状态为 `in_maintenance`；不产生新的组成变更或新决定。
6. **待检查（4 组）**：组已组装但尚无组级检查；使用决定为 `deferred` 并写明 `missing_evidence_reason`，组状态为 `pending_inspection`。
7. **检查不通过（3 组）**：初装检查为 `fail`，决定为 `rejected`；组状态为 restricted / retired。

### 5.4 使用决定与检查证据规则

- `allowed`：必须至少引用 1 份**同组、同 `composition_as_of`** 且结果为 `pass` / `pass_with_observation` 的检查；12 次允许决定附带使用限制（`use_restrictions`），对应组状态为 `restricted`。
- `rejected`：可以引用检查（如检查失败、组成不满足设计要求），也可以因缺少证据而拒绝，但要有理由；本数据 5 次拒绝均引用检查证据。
- `deferred`：4 次，全部因缺少组级检查证据，必须填写 `missing_evidence_reason`。
- `composition_as_of` 统一取“该组成开始生效的时刻”（初装作业结束、换件作业结束、移出生效时刻），与安装表半开区间配合可还原当时成员。

### 5.5 组业务状态（快照）

| `business_status` | 数量 | 判定口径 |
|---|---:|---|
| `available` | 138 | 最近一次决定为 allowed 且无使用限制 |
| `restricted` | 15 | 最近一次决定为 allowed 但带限制，或为 rejected 且仍保留修复可能 |
| `pending_inspection` | 4 | 最近一次决定为 deferred（尚无检查证据） |
| `retired` | 2 | 检查失败或拆件未补，退出原定服务 |
| `in_maintenance` | 1 | 快照时维护/诊断进行中 |

| ① 资产/事件 | `battery_unit.unit_id`、`organization.organization_id`、`lifecycle_event.event_id` | 23 条组级维护事件（写入共享 `lifecycle_event`）；电池组身份 `pack_id` / `pack_code` | 不修改既有 1,200 条事件；组所有权仍未建字段，待①/⑤接口确认 |
| ② 诊断 | 不新增读取 | 组级检查的 `method_ref` / `method_version` 采用统一命名 | 检查明细粒度待②确认；本数据只保存检查摘要与证据引用 |
| ③ 资格 | `assessment_id`、`unit_id`、`status`、`final_purpose_id` | 成员实际安装、组级检查与使用决定 | 每一条安装都引用评估；组包只接受 final + P01–P09 |
| ⑤ 租赁 | 暂不读取合同/租期 | `pack_id`（TEXT UUID）、`pack_code`、`V_PART4_PACK_SERVICE_STATE`、`V_PART4_RELEASE_EVIDENCE` | 第⑤板块租赁明细请引用 `pack_id`；可出租性需结合第⑤板块合同占用判断，第四板块的 `available` 不等于可出租 |

### 8.1 建议第⑤板块使用的查询

```sql
-- 组当前状态 + 最近一次使用决定
SELECT pack_id, pack_code, business_status, latest_release_code,
       latest_purpose_id, latest_decision_result, current_member_count
FROM V_PART4_PACK_SERVICE_STATE;

-- 某用途下允许使用、且当前仍有有效组成的电池组
SELECT s.pack_id, s.pack_code, s.latest_purpose_id, s.business_status
FROM V_PART4_PACK_SERVICE_STATE s
WHERE s.business_status IN ('available', 'restricted')
  AND s.latest_decision_result = 'allowed'
  AND s.current_member_count > 0;
```

## 9 合库与复现步骤

### 9.1 直接使用（推荐）

`data/section4_integrated.sqlite` 已经是第 1–4 板块的完整快照（23 张表 + 视图），可直接用于演示查询。若全组尚未合并第⑤板块，可在此基础上继续添加第⑤板块表。

### 9.2 从「合库」提取文件合并

1. 以包含第①–③板块的权威整合库为基础（如 `section3_eligibility_整合库.sqlite`）。
2. 执行 `sql/section4_schema.sql` 创建第四板块的 7 张表、索引与触发器。
3. 先把 `sql/section4_lifecycle_event_addon.sql`（或 `section4_lifecycle_event_addon.csv`）导入 `lifecycle_event`；该表已有数据时只追加，不覆盖。
4. 按外键顺序导入 7 张表的数据：`BATTERY_PACK → MAINTENANCE_EVENT → ASSEMBLY_JOB → BATTERY_PACK_UNIT → PACK_INSPECTION → SERVICE_RELEASE → SERVICE_RELEASE_INSPECTION`。可用 SQLite `ATTACH 'data/section4_synthetic.sqlite' AS s4;` + `INSERT INTO ... SELECT ... FROM s4....`。
5. 执行 `sql/section4_views.sql` 创建视图。
6. 运行 `python scripts/validate_section4_data.py`，确认 72 项检查通过。

上述步骤可合并为一条命令（脚本会自动按外键顺序导入并在结束时做校验）：

```bash
# 先复制一份第①–③板块权威整合库，例如 full_1_4.sqlite
python scripts/merge_section4_data.py --target full_1_4.sqlite --package-dir .
# 数据包解压目录中：
python scripts/merge_section4_data.py --target full_1_4.sqlite
```

已用第三部分交接库验证：合库结果与 `data/section4_integrated.sqlite` 的 7 张表逐行一致；
第①–③板块 15 张表的行逐行未变，`lifecycle_event` 仅新增 23 条维护事件。

> 若第①–③板块的整合库版本与交接版不同，先核对 `battery_unit`、`ELIGIBILITY_ASSESSMENT`、`USE_PURPOSE`、`organization` 的键值是否一致；不一致时不要直接导入第四板块数据，应先重跑生成器。
>
> PostgreSQL 最终实现时，把 TEXT 时间列映射为 `timestamptz`、触发器规则改为约束/延迟约束或应用层事务校验；本 SQLite 版本用于数据快照与合库验证。

## 10 与组内设计稿的差异与待确认事项

| 项目 | 组内 2026-11-16 汇稿/11-12 关系模式 | 本次数据实现 | 说明 |
|---|---|---|---|
| `pack_id` 类型 | integer | TEXT UUID v5 + `pack_code` | 对齐第①板块 TEXT 键；第⑤板块引用前请确认 |
| `maintenance_id` 类型 | integer | TEXT UUID，等于父事件 `event_id` | 维护子类型必须继承同一标识 |
| 使用决定的用途字段 | 汇稿 `purpose_id`；11-12 稿 `purpose_ref` | `purpose_id` INTEGER → `USE_PURPOSE` | 与第③板块用途字典直接对接 |
| 组所有权 | 未落到字段 | 未建字段 | 待①/⑤确认接口；当前不复制组织名称到组上 |
| `join_order` / `remove_order` / `composition_order` | 可空，同刻变化时使用 | 全部 NULL | 本数据时间戳可唯一区分，无需业务顺序 |
| `source_missing_reason` | 历史缺失时填写 | 全部 NULL | 合成数据不跳过可追溯性 |
| 待检查/暂缓组 | 规则允许 | 4 个组 | 对应 `deferred` + `missing_evidence_reason` |
| `BATTERY_PACK.formed_at` | 未成组可空 | 全部有值 | 本数据所有组均已实际形成 |

仍建议全组确认的事项：

1. 第⑤板块是否接受 TEXT `pack_id`（否则需在第⑤板块建立自己的映射）。
2. 组所有权、租期内改组/维护规则（Q03、Q09）。
3. 检查证据粒度与②板块统一检查框架（Q06）。
4. 使用决定的有效期、撤销与复查规则（Q08）。
